# Full system backup

`database/system-backup.sql` is additive and must be installed before this release. Only `service_role` can execute the snapshot/recovery functions. `database/sign-reference-indexes.sql` adds three FK indexes without modifying business records.

Production `/api/backup` exports CRM state, KPI, questionnaires/default templates, activity quantity rules/work outputs, all public Sign tables, Codeks portal links, audits, private work-log audit/recovery records, and financial/evidence state rows. Preview and rotating backup rows are excluded. Employee authentication is regenerated by the existing atomic core restore; login-throttle counters are transient, not business records.

Additional domains are read through small ordered pages, with fingerprints/counts/schema checked before and after the export. Live export does not take long SHARE locks. If records change during copying, the run fails without replacing the previous independent backup. PDF rows use pages of five; private audit history uses pages of 250. Each run creates an immutable private Vercel Blob object (30 days retained, including multiple copies per day), read back from the origin (`useCache:false`) and checked against a SHA-256 document manifest. The database copy stores small content-addressed compressed pieces (at most 700,000 base64 characters each). Every piece is read back and hash-verified before the core backup manifest is written. Unchanged pieces are reused; PDFs are grouped per record so new audit rows do not duplicate the full PDF archive. The manifest includes ordered groups, schema and the full-domain checksum; `readDatabaseArchive` reconstructs and verifies it. No single large domain archive is POSTed to PostgreSQL. Manual owner exports stream JSON with backpressure handling. Snapshot/backup errors are not success.

A full pre-repair database copy was separately captured in bounded `backup-system-before-repairs-20261031*` rows, with all 21 domain counts/fingerprints read back and verified. These are safety records, not new work logs.

Owner UI restoration is a dry-run only. Applying a backup requires the existing separate server authorization. Before any apply, save/read back an emergency private copy. Domain recovery inserts missing records only: it never rewrites/deletes signed history, disables immutable triggers, or silently overwrites changed finance/evidence rows. A conflicting existing row, changed schema, or concurrent write aborts the whole transaction. Newer legal records survive recovery. Core/Q/quantity recovery remains atomic with revision checks. An older backup omitting extra domains preserves the current domains. Actual disaster recovery should be rehearsed on a separate database of adequate capacity before any production apply.

Tests include real disposable PostgreSQL recovery of PDFs/seals, generated columns, identity sequences, finance originals, review answers, hours, amounts and quantities; append-only recovery/conflicts/full rollback; bounded-page exports; stale-manifest rejection; archive corruption and Unicode/backpressure streaming. No production restore is used for verification.
